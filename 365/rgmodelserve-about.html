The gateway

The interface stays steady while the engines change.

Local applications do not need to know which runtime loaded a model, which response format it emits, or whether enough memory is free. RGModelServe absorbs those differences behind one catalog and one compatible request surface.

ROUTING

The model name chooses the engine

Ollama handles its native fleet. llama.cpp serves GGUF models that need their own context, quantization, or runtime settings. An optional remote route can join the same catalog without changing the client.

TRANSLATION

Different streams become one contract

The gateway accepts both OpenAI-compatible and Ollama-native requests. It can pass streams through directly or translate between SSE and NDJSON so each interface receives the shape it expects.

CAPACITY

The requested model gets the machine

The coordinator unloads competing models, starts the required local backend, and applies model-specific context settings. Limited memory becomes a managed resource instead of a manual ritual.

VISIBILITY

Clients can see the available fleet

Health, catalog, active-model, and request-activity surfaces show what can run and what is running. Optional remote usage can also be measured and capped at the gateway boundary.

RGModelServe separates interface work from inference infrastructure. RGInfV1, Hermes, and future clients can keep a stable relationship with “the model,” while the gateway handles local runtimes, backend quirks, memory pressure, and route selection underneath.
